# 报告整合与界面

页面按四段组织：01组件能力 → 02项目地址与基本风雪压 → 03安装条件 → 风雪对比结果及报告。
表格每个灾种一行：组件能力、当地需求范围、不利占用比例、风险等级。计算依据、来源、缺口、复核事项分开展示，避免把意见重复堆叠。

独立页面可以下载JSON和Markdown；从/evaluation进入时带入work_id、案件ID、项目地址、型号及pvLoadScreeningInputText。参数保存到当前案件草稿，旧报告标记待重测。更换案件、地址或型号后不能拿旧风雪结果直接合并。

正式整单输入字段为pv_load_screening_input；正式整单输出字段为pv_load_screening_assessment。统一接口/assess输出包裹字段为assessment，不要混用字段名。

整单报告保留材料审核、照片风险、核保规则命中与决策，在风雪段只使用统一模块结果；新记录的catastrophe_assessment置空，避免旧历史天气算法重复输出。原风雪独立页/pv-load-screening重定向/risk-lab。

合并报告经服务端校验并新建案件，再计算决策。原人工审核作为原案件记录保留，不默认变成新案件的审批结论。前端IndexedDB同步新案件，业务系统接入时应在自己的存储中完成相同版本控制。

# 输出给核保人员的解释模板
“项目匹配到XX城市/站点10年基本风压XX kN/m²、基本雪压XX kN/m²。在已确认或估计的安装条件范围内，风需求为XX～XX Pa，组件正面对比能力XX Pa，占用XX%，风风险XX；雪需求XX Pa，雪对比能力XX Pa，占用XX%，雪风险XX。整体XX。尚需补充XX，明确拒保规则及其他风险另列。”

数字缺失必须写待评估，不能写0。风雪高等级应提示复核条件及能力，不自动捏造加费比例。
